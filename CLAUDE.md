# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A **pre-built Claude Code configuration bundle for timed take-home assignments**. When an assignment starts
the clock is already running, so none of it should go to creating `.claude/` directories, writing permission
allowlists, or approving MCP servers one prompt at a time. That work happens here, in advance.

It is not an application. There are no dependencies, no test runner, and no build step — `package.json`
exists only to give `bootstrap.mts` an npm script. Working here means editing Markdown and JSON.

## Commands

From this repo, whenever the bundle changes:

```bash
npm run bootstrap        # writes boot/claude-config.zip
```

Then at assignment kickoff, from inside the assignment directory:

```bash
unzip ~/SynologyDrive/Projects/assignment-prep/boot/claude-config.zip
```

Packaging into a zip rather than copying directly is what keeps the run-here/use-there split clean: `npm run`
only works from inside the package that defines the script, so a copy-to-target command could never be run
from the assignment directory where you actually want it. The zip decouples the two — build it whenever,
unzip it wherever.

**No dependencies — never run `npm install` here.** The zip is written by a small writer over `node:zlib`, so
there is nothing to install.

Node runs the TypeScript directly via native type stripping (Node 22.18+ / 23.6+; on 22.6–22.17 add
`--experimental-strip-types`). Node instead of shell so the same script works on macOS, Windows, and Linux.

Type stripping erases types without checking them, so the file must stay **erasable** — no enums, no
namespaces, no parameter properties. `.mts` rather than `.ts` so it's unambiguously ESM
(`import.meta.url` keeps working) even if a `package.json` later appears.

`unzip` prompts before replacing an existing file, which is the behavior you want when the assignment repo
already ships its own `.claude/` — `unzip -n` to skip those outright, `unzip -o` to overwrite without asking.

`boot/` is gitignored: it's build output, regenerated by the command above.

A missing source file or directory is reported under `not found, skipped:` rather than aborting the build —
a half-filled bundle is the normal state of this repo, so `.mcp.json` or a whole `.claude/` subdirectory
going away should still produce a usable zip. Filenames are copied verbatim — nothing is rewritten on the
way in.

The bundle's contents are the `INCLUDE` list at the top of `bootstrap.mts` — an include list rather than an
exclude list, so anything added to this repo stays here unless it is put on the list. `CLAUDE.md` and
`README.md` are simply not on it: they document the bundle rather than belonging to it, and shipping them
would drop assignment-prep notes into an employer's repo. An entry may name a directory (walked
recursively) or a single file.

It deliberately does **not** touch the target's `.gitignore`. Claude Code's automatic global-excludes
handling for `settings.local.json` only fires when Claude Code itself writes that file, so bootstrap prints
a reminder instead — silently editing an employer repo's `.gitignore` would surface in the diff a grader
reads.

## Layout

The repo's own `.claude/` **is** the bundle — there is no separate `bundle/` directory. Bootstrap copies
these files directly. That means the config active while working *in* this repo is exactly what ships to an
assignment, so breakage gets noticed here rather than under the clock.

```
.claude/
├── settings.json                  # committed; travels with the bundle
├── settings.local.json            # local scope; tracked here, copied as-is
├── rules/                         # standing constraints on how code is written
├── skills/                        # procedures Claude follows, invoked as /name
└── agents/                        # subagent definitions
.mcp.json                          # project-scoped MCP servers (playwright)

README.md                          # how to use the bundle; not part of it
CLAUDE.md                          # why it is built this way; not part of it
```

The three directories hold only a `.gitkeep` (git won't track an empty directory). They're empty on purpose —
see Current state below.

## The two settings files, and why they're split

Precedence runs: managed > CLI args > **local** > **project** > user.

**`.claude/settings.json`** (project scope, committed) holds `permissions.defaultMode: "plan"` and an
empty `permissions.allow` — the list is a slot to fill per assignment, once the real script names are known.

`plan` is deliberate and matches the global `~/.claude/settings.json` setting. An assignment is read before
it is written: the planning round-trip at the start of a session is worth more than the seconds it costs.
`acceptEdits` (auto-approve edits) and `auto` (auto-approve tool calls with background safety checks) are
the looser alternatives. Don't "fix" this to either one.

**`.claude/settings.local.json`** (local scope) holds `enableAllProjectMcpServers: true`.

This one is load-bearing and easy to get wrong: **as of Claude Code v2.1.196, `enableAllProjectMcpServers`
is honored in an untrusted folder only from settings files that are not checked into the repo.** A freshly
cloned assignment repo is exactly that case, so putting this key in the committed `settings.json` would
silently do nothing. Keep it in the local file.

It ships under its real name — no `.template` suffix, no rewriting on copy. That means `.gitignore` must
**not** ignore `.claude/settings.local.json` in this repo: the bundle can only ship a file git is tracking,
and ignoring it is what silently produced a five-file zip with this key missing. The usual reflex to ignore
`settings.local.json` is wrong here, because in this one repo that file is source, not local state.

**Permission rule syntax** — `Bash(npm run:*)` and `Bash(npm run *)` are equivalent; `:*` is only recognized
at the *end* of a pattern, so `Bash(git:* push)` treats the colon literally and matches nothing useful. The
space before `*` enforces a word boundary: `Bash(ls *)` matches `ls -la` but not `lsof`, while `Bash(ls*)`
matches both.

**No hooks are configured.** Other repos here use `Stop → npm run lint` (see `koalires`, `cobidiex`), which
is worth adding once an assignment's stack is known — but it fails in a repo with no `lint` script, so it
can't ship in a stack-agnostic bundle.

## Current state

**Skeleton only.** `rules/`, `skills/`, and `agents/` are empty, and `permissions.allow` is an empty list.
Don't assume a skill exists — check before referencing one.

The intended next step is authoring stack-agnostic skills (kickoff, verify, commit, submit). Bootstrap is
intentionally minimal for now; project detection and stack presets were considered and deferred.

## Conventions

Slash commands are skills — there is no separate commands concept. For project and personal skills the
`/name` comes from the **directory name**: `.claude/skills/verify/SKILL.md` is `/verify`, and frontmatter
`name` is only a display label. (A legacy `.claude/commands/*.md` file still loads, but nothing new should
go there.)

Working examples elsewhere on this machine: `../sadmo/.claude/skills/commit/SKILL.md`,
`../chromium-filler/.claude/skills/push-main/SKILL.md`, `../koalires/.claude/skills/sync-agents/SKILL.md`,
`../kirva/.claude/agents/`, and the reference layout at `../prompt-aing/example-structure/`.

Claude Code's settings surface changes often enough that recalled details go stale. Verify against
https://code.claude.com/docs before adding a settings key or frontmatter field.
